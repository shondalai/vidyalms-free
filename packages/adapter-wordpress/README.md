# VidyaLMS WordPress adapter (the `vidyalms` plugin)

The WordPress shell around the CMS-agnostic VidyaLMS core. It supplies the core with users,
database, permissions, files, mail, scheduling, events, commerce, translation and caching, and adds
routing, admin screens, blocks and a REST mount. It contains no learning rules: every write goes
through a core use case, and anything that passes the contract on Joomla and fails here is an
adapter bug by definition.

Requires WordPress 6.6 and PHP 8.1. One plugin directory, `vidyalms/`, is what ships to
wordpress.org.

## Frontend theme layout

Routed learner pages use the theme's wide content size (or its content size when no wide size
is defined) and root side padding. The catalogue, learner dashboard, course player and other
learner routes share this open, transparent container. It stays outside the SPA replacement
area. Embedded blocks and shortcodes keep their existing host container.

Classic themes without these WordPress CSS variables fall back to a 1280px maximum and
responsive 16 to 32px gutters. Themes can set `--vidyalms-theme-width` to change the maximum or
`--vidyalms-theme-gutter` to change the fallback gutters. The route marker on the body is
`vidyalms-site`; the `.vidyalms` styling scope belongs only on LMS content, so the site's
header, footer, typography and links retain the theme's styles.

## How the ports map onto WordPress

| Port | Implementation | Notes |
|---|---|---|
| Database | `WpDatabase` | `$wpdb`, tables `{$wpdb->prefix}vidyalms_*`. Compiles the core `Query` with `prepare()` placeholders only. |
| Users | `WpUsers` | `WP_User`. The core sees an id, a display name and an email; profile fields stay in WordPress. |
| Authorization | `WpAuthorization` | Capabilities on roles. The core's capability vocabulary (`vidyalms.teach`, `vidyalms.grade`, `vidyalms.enrol` and the rest) maps to WordPress capabilities granted by the activation hook. |
| Storage | `WpStorage` | Public assets use `uploads/vidyalms`. Private I/O requires `VIDYALMS_PRIVATE_DIR` in server configuration, outside the site, content, uploads and document roots. The in-uploads default fails closed before any private directory or guard is created. Database settings cannot select an absolute path or another folder. Guards are defense in depth. Signed downloads pass through the same path and symlink checks. |
| Mailer | `WpMailer` | `wp_mail`. A message the core rendered is sent as authored, multipart with the plain part first; a template-addressed one is rendered from the core catalogue as before. The header map travels in the headers array, and `AltBody` and the envelope `Sender` are set on `phpmailer_init` for the duration of one send. See [the mail port](#the-mail-port-and-what-php-mail-does-to-a-structured-header). |
| Scheduler | `WpScheduler` | Writes `{prefix}vidyalms_wp_jobs`, drained by `Jobs\QueueRunner`. Action Scheduler fires each job punctually where it is installed; the recurring WP-Cron event is the fallback and the safety net. |
| Events | `WpEventBridge` | `do_action('vidyalms/course_completed')` and the rest, each fired once with a stable idempotency key. |
| Commerce | `WpCommerce` | Asks the `vidyalms_course_price` and `vidyalms_course_purchase_url` filters; the WooCommerce bridge answers them. First usable answer wins. |
| I18n | `WpTranslator` | A core key resolves through `src/I18n/catalogue.php` to English, then through the literal `_x()` call in `src/I18n/gettext.php` with the key as the context. |
| PDF | none in this plugin | `Ports::$pdf` is whatever the `vidyalms_pdf_port` filter answers while the Ports are built, null by default. The VidyaLMS Pro add-on answers it with its own renderer; without one, certificates render as HTML. |
| Cache | `WpCache` | Object cache and transients, invalidated by domain events. |
| Clock | `SystemClock` | Always UTC. |
| Random | `WpRandom` | `random_bytes` and `random_int`. |
| Logger | `WpLogger` | PSR-3 over the WordPress debug log. |
| Course categories | `WpCourseCategories` | Native `vidyalms_course_category` terms. Count, own-name search and stable paging stay in MySQL; full `Parent / Child` labels are hydrated only for the returned page. Manager/edit URLs are present only for callers with `vidyalms_manage`; assign-only instructors remain in the LMS picker. Writes remain on WordPress's native Categories screen. Native terms and LMS rows cannot share a portable lock, so a concurrent delete is exposed later as a recoverable missing category rather than hidden. |

HTTP, routing and privacy have no core port interface: they are adapter-side by design, which is
why `src/Rest`, `src/Content` and `src/Privacy` talk to the kernel rather than implementing a port.

There is exactly one `CoreKernel` per request, reached through the global accessor
`vidyalms_kernel()`, and one `Ports` bundle, reached through `vidyalms_ports()`. Nothing constructs a
second kernel: that would mean a second event bus and a second idempotency store. Classes that need
either take a resolver in their constructor and fall back to the global accessor, so they can be
unit-tested without WordPress.

## The integration surface

Everything below is a published name. Another plugin, a theme or the Pro package may rely on it.

**Reaching the engine.** `vidyalms_kernel()` returns the one `CoreKernel`; `vidyalms_ports()`
returns the one `Ports` bundle; `vidyalms_system_principal()` returns the actor background work runs
as. The same three, plus `database()`, `storage()`, `scheduler()`, `translator()`, `path()` and
`url()`, are static methods on `Shondalai\VidyaLMS\WordPress\Plugin`. Code that cannot name the
class asks the `vidyalms_kernel` and `vidyalms_database` filters instead.

**Actions.** `vidyalms_kernel_ready` fires once, with the kernel, before anything has used it: that
is where a provider is registered into `$kernel->registries`. Adding a key is `register()`, which
throws on a duplicate; overriding one the free build already registered is `replace()`, which hands
back the provider it displaced so the replacement can delegate to it. The adapter applies
`Provider\SiteSelfEnrolmentRule` before the hook and again in a finally block afterwards. Every
registered enrolment rule, including newly added context-aware Pro rules, obeys the site switch.
`vidyalms_booted` fires on `plugins_loaded` once every subsystem has booted. Domain events arrive
as `vidyalms/course_completed` and the rest, each with `(array $payload, string $idempotencyKey,
DateTimeImmutable $occurredAt)`.

What a `vidyalms_kernel_ready` listener receives, exactly:

| | |
|---|---|
| Action | `vidyalms_kernel_ready` (`Plugin::HOOK_KERNEL_READY`) |
| Arguments | one: the `CoreKernel` for this request. Nothing else, ever; a listener that needs more asks the kernel |
| Fires | once per request, lazily, the first time anything calls `vidyalms_kernel()`, `Plugin::kernel()` or the `vidyalms_kernel` filter |
| A listener may | `register()` and `replace()` on any of the sixteen registries, add routes with `addRoutes()`, and read `$kernel->registries` |
| A listener must not | keep the kernel past the request, or call `vidyalms_kernel()` from inside the listener |
| A listener that throws | is logged and swallowed; whatever it registered before it threw stays registered, and the listeners queued behind it are skipped, which WordPress gives no way to isolate |

Register on it at file scope or on `plugins_loaded`, not later: the kernel is built on demand, and a
listener added after the first build has missed it. **Every context it fires in**, proved by
`build/kernel-ready.php` rather than asserted here:

| Context | Reached through |
|---|---|
| Site request | a course or catalogue page, a shortcode, a block |
| wp-admin | the settings, workbench and screen pages |
| REST | `/wp-json/vidyalms/v1/...` and the host upload route |
| WP-CLI | `vidyalms_kernel()` from a command |
| WP-Cron | `Jobs\QueueRunner` on `vidyalms_run_jobs`, or Action Scheduler on `vidyalms_run_job` |

```
php build/kernel-ready.php [--wp=<wordpress root>] [--url=<site url>]
```

The listener it uses is a real must-use plugin, written before the run and deleted after it, because
that is what a third party is: code WordPress loads before this plugin, registering on an action that
has not been declared yet. It fetches the front end and the REST route over HTTP and loads the other
three in process with the constants their own entry points define (`WP_ADMIN`, `WP_CLI`,
`DOING_CRON`), and in each one the listener registers a provider and has the core run it. It writes
two files inside `wp-content/mu-plugins` and removes both, and it removes the folder again if it had
to create it.

`vidyalms/course_created`, `/course_published`, `/course_updated` and `/course_archived` are the
core's own course events, delivered like every other one. `Content\CourseSync` listens to them and
keeps the permalink shell in step: a published or renamed course rewrites its post, an archived one
trashes it, and the map survives so republishing lands on the same URL.

It used to work the other way round. The use cases dispatched no event of their own, so whichever
layer called them had to fire the action, and when that layer became the React workbench
`CourseSync` started listening on `rest_request_after_callbacks` and recognising a successful write
on a path beginning `/vidyalms/v1/manage/courses`. That was adapter-side knowledge of the contract's
URL shape and it was wrong in both directions: a course created by an importer, by WP-CLI or by a
Pro package got no shell, while a future contract path could have picked one up by accident. There
is no route knowledge left in this adapter; the shell follows the record however the record was
written.

The four action names are unchanged, because they are a published extension point: a plugin that
fires `vidyalms/course_published` itself with a `Course`, an array or a slug is still understood.
What changed is that nothing has to.

**Filters.** `vidyalms_course_price` and `vidyalms_course_purchase_url` are what `WpCommerce` asks.
`vidyalms_user_can_course` is the per-course authorization seam. `vidyalms_verification_base_url`,
`vidyalms_system_user`, `vidyalms_mail_headers` and `vidyalms_log` do what their names say.
`vidyalms/self_enrolment_enabled` decides whether learners may enrol themselves, defaulting to the
site setting. It is read in one place, `Provider\SiteSelfEnrolmentRule`, so answering it refuses
every path and not only the page that renders the button. `vidyalms_upload_max_mb` takes
`(int $megabytes, string $purpose)` and is how a site raises or lowers what the file picker accepts;
PHP's own `upload_max_filesize` and `post_max_size` still apply on top and are usually the number
that binds.

**Extra client bundles.** `vidyalms_mount_bundles` takes `(array $bundles, string $mount)` and is
how a package loads a second JavaScript bundle beside one of the four apps: a question type
renderer, a lesson type renderer, anything that registers into a global the app publishes. The four
mount names are the four bundle names, `player`, `quiz-runner`, `instructor` and `admin`, and the
filter is asked once, at the moment that app is enqueued. Answer with a list of
`['handle' => ..., 'src' => ..., 'version' => ..., 'style' => ..., 'module' => ...]`; only the first
two are required. `Assets\MountBundles` states the whole contract.

Ordering is the reason this is a filter rather than a documented `wp_enqueue_scripts` hook. A
contributed bundle reads globals the app publishes at its own module scope, so it has to run after
the app, and "later in the document" is not the same as "after": an ordinary classic script placed
after a module tag runs while the document is still parsing, which is before any module runs. So the
contributed bundle is enqueued as a script module where WordPress has them and as a deferred classic
script otherwise, behind the app in both cases. A package that hooked `wp_enqueue_scripts` itself
would have to solve that a second time, and would have to guess which admin screen is the workbench.

Nothing free depends on it. With no listeners the pages load exactly what they loaded before it
existed, which is what the Pro plugin's own harness asserts on a site where Pro is not installed.

**Uploads.** `POST /wp-json/vidyalms-host/v1/upload` is the host's file intake for the React apps,
deliberately outside the `vidyalms/v1` contract namespace: the contract carries no bytes, and a
route invented in it would answer here and 404 on Joomla. One multipart `file` plus a `purpose`;
the caller needs `vidyalms.teach` or `vidyalms.manage`, asked of the core's guard. The free build
registers two purposes, `resource` (documents and archives, `putPrivate`) and `image` (raster
images only, `putPublic`), and a plugin adds or narrows one on the `vidyalms_upload_policy` action:
`register()` throws on a duplicate key, `replace()` hands back what it displaced. Every purpose,
whoever registered it, goes through the same intake: the extension is checked against the purpose,
the media type is sniffed from the bytes and has to be one that extension may carry, an image has
to decode as a raster image, and the stored path is generated from a random token rather than taken
from the client. The answer is `{path, name, size_bytes, mime, url}`, the shape a resource lesson's
`files[]` already stores. See [04-api-contract.md](../../docs/technical/04-api-contract.md).

### Private storage deployment and migration

With a writable parent outside the web root, web setup selects a site-specific external
directory automatically. The saved location carries an HMAC under the server's WordPress
salt and site identity, so a database edit cannot redirect private I/O and CLI workers use
the same location. CLI-only first installs wait for a web request or explicit configuration.
Clones must configure their own directory; they cannot reuse the original site's signed record.
If automatic setup is unavailable, or to choose another location, set this in the site's
`wp-config.php`, before loading `wp-settings.php`:

```php
define('VIDYALMS_PRIVATE_DIR', '/srv/vidyalms-private/wordpress');
// Windows example instead: define('VIDYALMS_PRIVATE_DIR', 'C:/vidyalms-private/wordpress');
```

Use a dedicated directory for each independent installation. Do not share one root
between unrelated sites or expose it through an alias, CDN or second virtual host.
Single-site installations use the constant unchanged. Multisite installations use
`<VIDYALMS_PRIVATE_DIR>/sites/<blog_id>`, including `/sites/1` for the main site.
Each blog gets separate certificates, reports, quotas and ownership metadata. The
shared base and `sites` parent are never claimed or recursively removed. Existing
multisite files must be moved into the correct blog directory only after verifying
which site owns them; there is no automatic migration or fallback to the shared base.
The administrator notice remains visible until the root passes read-only safety and
writability checks. It never creates folders during page rendering.

On a site that kept the default, the source is
`<wordpress root>/wp-content/uploads/vidyalms-private` and the destination is the
directory named by `VIDYALMS_PRIVATE_DIR`. A previous custom configuration may
use another source; inventory the actual source before changing configuration.

1. Pause web uploads/imports and queue workers. Record the source/destination absolute
   paths and back up the files and database. Verify the destination is outside
   the web server's document root and all other served roots; reject symlinks/junctions in both trees.
2. Copy to a new empty destination without following links or overwriting files.
   Preserve relative paths, including `.secrets` where present. Compare the complete
   file inventory, byte counts and SHA-256 digests before switching configuration.
3. Give only the required web/worker accounts access (0700 directories and 0600 files
   on POSIX; restricted ACLs on Windows). Allow the directory in `open_basedir` for
   both web and CLI. Set the constant and restart relevant long-running workers.
4. Verify an upload, signed download and queued import on the web and worker paths.
   Verify that public HTTP cannot fetch a private file directly. Remove the old
   web-root copy only after verification, with writes still paused; retaining it
   under the web root leaves the original disclosure risk. Keep backups outside
   served directories. Resume work only when both the new root and old-URL refusal
   are verified. A config rollback must not restore an exposed private root.

No migration is automatic, and changing a database path option does not migrate or
re-enable storage. These instructions are a deployment handoff, not evidence that a
particular live host has been migrated.

### Private-root ownership and uninstall contract

Hosting that permits a proven external directory can use automatic setup. `Settings::privateStorageDir()` returns
the configured **base**, and `WpStorage::resolvePrivateRoot($uploadsBase, $configuredBase)`
resolves the current blog. `privateRoot()` returns that captured per-site directory.
A storage instance fails if reused after switching sites; resolve a new instance.
Signed-download signatures also include the network/blog identity to prevent replay
between blogs sharing WordPress salts.

The standalone `Files\PrivateStorageOwnership` helper requires only WordPress,
not the plugin bootstrap or generated core loader. Uninstall can explicitly require
`src/Files/PrivateStorageOwnership.php` and call:

- `resolveRoot($uploadsBase, $configuredBase)`: same resolver used by WpStorage.
- `isOwned($root)`: true only for a valid current-site marker; false for an
  absent marker; throws for a malformed, linked or foreign marker. The caller must
  also check the intended root boundaries and reject links during recursive deletion.
- `claimIfEmpty($root)`: called by storage after validating an external, writable
  root, before writing its guard files. Only an empty root is claimed; a valid
  marker is reused. A nonempty unmarked root refuses reads, writes and deletion until verified by the server owner.
- `markerContentsForCurrentSite()`: server-owner-only migration helper. It creates
  or reuses the site's database token and returns JSON, but does not write a marker.
  Install those bytes manually only after quiescing writers and verifying the entire
  nonempty root belongs exclusively to this site. Never mark an arbitrary directory.

`MARKER` is `.vidyalms-owner.json`. Version 3 records `version`, `network_id`, `blog_id`,
`site_url`, `installation` (SHA-256 of the canonical ABSPATH, case-normalised on Windows),
and `site_token` (64 lowercase hex characters). Older markers are not silently upgraded.
Single-site installations use network ID 0. In multisite the network ID comes from
`get_site(get_current_blog_id())->network_id`, not the possibly stale global network
context after `switch_to_blog()`. `TOKEN_OPTION` is `vidyalms_storage_site_token`,
a non-autoloaded, per-blog option containing 32 random bytes encoded as 64 hex characters.
The token survives signing-salt changes; the marker binds the site URL and installation path.
Back it up with the database. Same-URL filesystem clones must use independent private roots.
For a legitimate address/server move, explicitly renew the marker using the helper above only
after confirming exclusive ownership and quiescing all writers at the old location.
Marker creation uses exclusive create and file locking; invalid/incomplete markers
fail closed and are never silently replaced. Ordinary storage paths cannot address
the reserved marker filename.

`WpStorage::ownsPrivateRoot()` exposes the same proof after the storage boundary
checks. A verified owned root authorizes lifecycle to remove **all** of that site's
private files, including unattached uploads, Moodle files, temporary stages and
secrets, when the site's uninstall preference requests deletion or the entire subsite is deleted. Lifecycle must
remove/check files before deleting `TOKEN_OPTION`. Data-retention uninstall must
retain the token. An absent marker never authorizes whole-root deletion; existing
reference-only cleanup is not sufficient proof of ownership. Foreign/malformed markers must stop
cleanup, not cause a fallback deletion. Never delete the multisite shared parent.

Existing nonempty directories require the verified manual marker step before use.
Automatic ownership is never retroactive: a copied database must not authorize
reading, overwriting or deleting another installation's unmarked files.

Automatic reference-aware expiry of saved orphan uploads remains a separate constraint.
There is no central upload/claim ledger: references occur in `submission_files.path`,
`lesson_content.content`, question definitions, frozen `attempt_questions.presented`,
`attempt_answers.answer/ui_state`, `attempt_answer_events.response`, public course
image URLs and provider-defined JSON. A file can also be awaiting a later draft save.
Scanning a few tables or deleting by age cannot prove it is abandoned, and a reference
can be attached between a scan and deletion. Safe expiry would need an upload ledger,
transactional claims/leases across these consumers, and a bounded sweeper. That system
is not introduced here. Quotas bound retained uploads; failed/staging cleanup and
existing terminal import-source retention remain active.

**Capabilities.** `vidyalms_admin`, `vidyalms_manage`, `vidyalms_teach`, `vidyalms_grade`,
`vidyalms_enrol`, `vidyalms_reports`, `vidyalms_manage_groups`, all constants on
`Setup\Capabilities`. Activation grants all seven to `administrator` and grants teach, grade, enrol
and reports to a new `vidyalms_instructor` role. Map a core key with
`Capabilities::wordpressCapability('vidyalms.teach')` rather than hardcoding.

`Admin\Menu::CAP_ACCESS` (`vidyalms_access`) is a meta capability, mapped through `map_meta_cap` and
never granted to a role: it means "holds any one of manage, teach, grade, enrol or reports", and it
is what the top level menu entry is drawn with. Gating the parent on `vidyalms_manage` would hide the
whole menu from an instructor, workbench included.

Ask the kernel's use cases, or `Plugin::ports()->authorization`, rather than a bare
`current_user_can`. `WpAuthorization` supplies an implication WordPress does not have:
`manage_options` grants every VidyaLMS capability except `vidyalms_admin`. Without it, an
administrator whose roles were reset by a security plugin or restored from a backup taken before
activation would open VidyaLMS and be refused by every screen in it.

**Settings.** The four an administrator edits live in one option row, `vidyalms_settings`, written
by `Admin\SettingsPage` through the WordPress Settings API and read everywhere else through
`Setup\Settings`: `verification_base_url`, `catalogue_per_page`, `self_enrolment`,
`private_storage_dir`. Four scalar options carry the rest: `vidyalms_schema_version`,
`vidyalms_version`, `vidyalms_activated_at`, `vidyalms_signed_url_ttl`,
`vidyalms_catalogue_show_locked` and `vidyalms_job_batch_size`, all constants on `Setup\Activator`.
Any new option has to be added to `Setup\Uninstaller::OPTIONS` or it survives a delete.

Private storage is server-owned. Web setup selects and records a site-specific directory outside
known public roots when writable; CLI workers reuse that signed record. To override the location,
define `VIDYALMS_PRIVATE_DIR` in wp-config.php as an absolute, dedicated directory outside
**all** public document roots, for example
`/srv/vidyalms-private/site` or `C:/vidyalms-private/site`.
Do not expose it through a server alias. Database values for `private_storage_path`
and `private_storage_dir` are ignored when resolving storage; runtime settings refuse
non-default changes. If neither automatic selection nor an explicit safe root is possible, private I/O
fails closed; public course images remain available. There is no fallback to public storage.
An unwritable directory, open_basedir restriction or public-root overlap fails closed. A canonical
root may have a symlinked ancestor; links inside stored paths remain forbidden.
Configure the same directory in web and worker contexts.

`UploadController` explicitly checks login and the core upload capability in its REST
permission callback. Learner assignment/attempt uploads require a current course enrolment; authoring
requires teach or manage. Both normal uploads and import sources use bounded reads,
shared extension/content validation and `wp_handle_upload()` with type checking enabled
and a generated name. Its temporary destination is a verified private directory,
never the media library. Filters and temporary files are cleaned up on success and
failure; interrupted staging older than 24 hours is reclaimed on subsequent uploads.

All upload purposes and import sources share locked per-user limits of 512 MiB,
500 stored files and 50 files in the last hour. Tiny and unattached files count;
deleting files releases capacity. Atomic writes remove incomplete temporary files.
Saved learner/author files are not expired blindly because they may be referenced by
active or historical work. Automatic reference-aware orphan expiry is not implemented;
unattached saved files remain bounded by these quotas. Existing import source retention
continues to apply. Moodle attachments use the resource allowlist and byte inspection,
and a SHA-256 content path with a fixed basename and validated suffix. Executable types
and mismatched contents are skipped with an import warning.

`privateRoot()` still reports the location without creating files; `privatePath()`
enforces the private boundary. Uninstall owns a separate checked deletion path and
must not interpret a failed private I/O check as permission to delete arbitrary roots.

Turning `self_enrolment` off is enforced in exactly one place. On `vidyalms_kernel_ready` the
adapter calls `replace()` on the enrolment rule registry and puts `Provider\SiteSelfEnrolmentRule`
in front of every rule, including context-aware Pro rules: with the switch on it delegates to whatever rule it displaced,
with the switch off it refuses. Every caller then gets the same answer, because every caller asks
the same rule. The enrol button is not rendered, a hand-built form POST comes back as a conflict
notice, `POST /enrolments` answers 409, and so does WP-CLI or another plugin calling `SelfEnrol`.

There is deliberately no second check in `Content\Templates` or `Rest\RestController`. Guards in an
adapter cover only the routes that adapter owns, and this plugin carried three of them before the
rule existed. The template asks the registry whether the rule allows the enrolment; it does not read
the setting.

**Private files.** `WpStorage::signedUrl()` points at `admin-post.php?action=vidyalms_file` with the
path, an expiry and an HMAC keyed on the site's auth salt. `Files\DownloadEndpoint` registers both
`admin_post_` and `admin_post_nopriv_`, because a certificate link is followed by whoever was sent
it, verifies the signature and streams exactly the path that verified. There is deliberately no
nonce and no capability check there: the signature is the authorization, and a nonce would refuse
the visitor the link exists for.

**Deferred work.** `WpScheduler` writes `{prefix}vidyalms_wp_jobs`; `Jobs\QueueRunner` drains it on
`vidyalms_run_jobs` (a five-minute WP-Cron event the plugin registers and heals) and runs one job on
`vidyalms_run_job`, which Action Scheduler fires per job where it is installed. Jobs are claimed
with a conditional update, retried with a backoff to three attempts, reclaimed after thirty minutes
stuck, and pruned thirty days after they finish. The same pass calls the core's `PruneImportSources`,
which deletes an uploaded import archive once every job naming it has finished and the last of them
finished more than `import_source_retention_days` ago (thirty by default, set on the settings screen).
The window exists because Retry on a finished import re-queues that same file; a source a queued or
running import still needs is never deleted, whatever its age, and a `cms-db:` source is not a file.
This is the same split as `plg_task_vidyalms` on Joomla. A third event,
`vidyalms_run_sweeps`, runs hourly and starts every registered sweep; see
[Starting the sweeps](#starting-the-sweeps).

**Adding a subsystem.** An autoloaded class is never loaded until something names it, so
`Plugin::SUBSYSTEMS` is the list that gets a class booted at all. Every entry is `class_exists`
guarded, so a class that is not in the list silently never runs and never fatals.

## The React apps and the REST nonce

All four apps from `packages/ui` run in this plugin: the player and the quiz runner on front-end
pages, the admin screens and the course workbench in wp-admin. Each page renders one mount div
carrying the whole host contract in a single attribute and loads one ES-module entry (through the
script modules API, with a `type="module"` fallback pre-6.5):

```html
<div id="vidyalms-player" data-vy-config='{"api":{...},"course":{...},...}'></div>
```

- **The player page** is the rewrite `/courses/{slug}/learn` (plus the
  `?vidyalms_route=learn&vidyalms_learn_slug=<slug>` query-var fallback), rendered by
  `templates/learn.php`. An optional `vy-lesson=<id>` deep-links a lesson. Guests are redirected to
  `wp-login.php` (and brought back) unless the course has at least one free-preview lesson. The course
  page and My Learning link here (Resume / Continue learning, `Rewrites::learnUrl()`), and for a visitor
  without an enrolment the course page links each free-preview lesson's title here with `vy-lesson`
  (the `preview_urls` of `Templates::courseContext()`).
- **The quiz runner** mounts on the handoff URL the player builds: the course permalink plus
  `vy-quiz=<lessonId>`. `templates/single-course.php` sees that parameter, `Content\LearnerApps`
  has already sent guests to login, and the quiz-runner mount renders instead of the course page.
- **The admin screens** are six wp-admin pages, one submenu entry each, all rendering the same `admin`
  bundle on `#vidyalms-admin`; the config's `screen` says which entry rendered it. They replaced the
  PHP dashboard, the two `WP_List_Table` screens and the PHP course form: creating, editing,
  publishing and archiving a course all go through the `/v1` management surface now, so there is one
  code path per rule rather than one per screen. Import is still a server-rendered screen, because
  bytes never travel through the REST layer.
- **The course workbench** is `admin.php?page=vidyalms-course&course=<id>`: one course and its five
  tabs, or the caller's own course list when the URL names no course. The slug in the mount config
  comes from `GetManagedCourse`, which applies the per-course rule; a caller who may not read that
  course gets an empty slug and the app renders the refusal the API gives it.
- **The instructor page** is the same workbench bundle on a front-end page: the `/teach` rewrite
  (`Rewrites::ROUTE_INSTRUCTOR`, slug filterable through `vidyalms/route_slug`) rendered by
  `templates/instructor.php`, and the `[vidyalms_instructor]` shortcode for a site that prefers its
  own page structure. Both render `templates/part-instructor.php` and the same `data-vy-config`, so
  the two cannot behave differently. The course rides as `?vy-course=<id>`, a mount-contract
  parameter read from the raw request the way `vy-lesson` and `vy-quiz` are, not a WordPress query
  var.

  `Content\InstructorPage::mountConfig()` writes the same contract `Admin\AdminApps::workbenchConfig()`
  writes, key for key, with front-end URLs. The page decides exactly two things: a guest is sent to
  `wp-login.php` and brought back, and everybody else gets the mount. There is no capability check
  here and no edition check anywhere: who may teach is the core's answer to `GET /manage/courses`, so
  a learner who finds the URL is refused by the API and the app renders the permission state designed
  for it. The role to put a teacher in, `vidyalms_instructor`, is created on activation by
  `Setup\Capabilities` and is part of the free plugin.
- **Authentication** is the browser session, front end and wp-admin alike: `/wp-json` cookie auth
  requires the `wp_rest` nonce, so the mount config's `api` block is
  `{"base": rest_url('vidyalms/v1'), "mode": "prefix", "headers": {"X-WP-Nonce":
  wp_create_nonce('wp_rest')}}` and `Rest\RestController` resolves the caller from
  `get_current_user_id()` exactly as before. WordPress has no separate administrator credential, so
  the administrator apps ride the same mechanism the learner apps do. Guests keep working for public
  paths; the core owns routing, authorization and every status code.

| Screen | URL |
|---|---|
| Dashboard | `wp-admin/admin.php?page=vidyalms` |
| Courses | `wp-admin/admin.php?page=vidyalms-courses` |
| Enrolments | `wp-admin/admin.php?page=vidyalms-enrolments` |
| Learners | `wp-admin/admin.php?page=vidyalms-learners` |
| Certificates | `wp-admin/admin.php?page=vidyalms-certificates` |
| Settings (the read-only mount above the WordPress options form) | `wp-admin/admin.php?page=vidyalms-settings` |
| Course workbench | `wp-admin/admin.php?page=vidyalms-course&course=<id>` |
| Instructor page (front end, same bundle) | `/teach/`, `/teach/?vy-course=<id>`, or `[vidyalms_instructor]` |
| Import (server rendered) | `wp-admin/admin.php?page=vidyalms-import` |

Settings carries both: the app's screen states what the engine is configured to do, which
`GET /admin/settings` answers read-only by contract, and the WordPress Settings API form below it
edits the four options this plugin owns. `urls.settings` in the mount config is that page plus the
`#vidyalms-wordpress-settings` anchor, so "open host settings" lands on the form.

The workbench is registered under the Courses slug rather than the top level one, which makes it an
addressable, capability-gated page WordPress never draws in the sidebar (it renders a submenu group
only for a slug that is also a top level menu). `remove_submenu_page()` is the more familiar way to
hide a page and it does not work: with the entry gone from `$submenu`, `get_admin_page_parent()`
resolves no parent, `user_can_access_admin_page()` then looks for the hook name `admin_page_<slug>`
while `add_submenu_page()` registered `<parent>_page_<slug>`, and the page answers 403 to everyone.

`Content\LearnerApps` builds the front-end config and `Admin\AdminApps` the administrator one (both
shapes fixed and shared with the Joomla adapter's `MountConfig` and `AdminMountConfig` services); each
guards its pages and enqueues only the bundle that page mounts. The bundles are a build-time copy of
`packages/ui/dist` (gitignored, cache-busted by the plugin version); their file names are fixed, and
all entry and chunk files sit flat in `assets/app/` so the entries' relative ESM imports resolve.

There is no admin script any more. `assets/js/admin.js` held the media picker, the slug helper, the
completion threshold toggle and the archive confirmation, all of which belonged to the PHP course form
and the PHP course list. `assets/css/admin.css` stays, and now holds only what is still rendered:
the page frame, the status pills and the Import screen and its job list. The dashboard cards, the
getting-started box, the progress bars, the list-table column widths, the course form and the media
picker preview went with the screens that drew them.

## The notification surfaces

Two pages, two shortcodes and one machine endpoint, all of them thin: each hands
a contract path to the core kernel and renders what comes back. None holds a
rule, and none knows which use case answers, because the routes are frozen by
`openapi.yaml` and the classes behind them are not this plugin's business.
`Content\CoreRoute` is the whole of the plumbing and `Content\CoreRouteResult`
is what a page reads, method for method the same class the Joomla adapter has,
because the two render the same states from the same answers.

| Surface | URL | Who reaches it |
|---|---|---|
| Unsubscribe | `/unsubscribe/{token}/`, or `[vidyalms_unsubscribe]` | anybody holding the link, with no session |
| Preference centre | `/notification-preferences/`, or `[vidyalms_notification_preferences]` | the signed-in learner, and nobody else's rows |
| Delivery feedback | `POST /wp-json/vidyalms-host/v1/feedback/{channelKey}` | an ESP webhook or a feedback-mailbox forwarder, with a shared secret |

Both pages are ordinary server-rendered templates, overridable from a theme's
`vidyalms/` directory like every other one (`unsubscribe.php`,
`part-unsubscribe.php`, `notification-preferences.php`,
`part-notification-preferences.php`). Neither is a React mount: they have to
work in whatever browser a mail client opens, and they inherit the theme's
accessibility conformance. The route slugs go through `vidyalms/route_slug`
like the rest.

**The unsubscribe page is one URL doing two jobs, because RFC 8058 gives a
receiver one URI.** A mail client that supports one-click POSTs to the URI in
`List-Unsubscribe`; a person who clicks the link GETs the same URI. Four rules
hold it together:

- **A GET acts on nothing.** It renders a confirmation form. Mail security
  scanners follow every link in a message, which is the whole reason RFC 8058
  specifies a POST, and a GET that unsubscribed would turn a scanner into an
  opt-out.
- **Nothing beyond the token is required.** No login, no nonce, no address to
  confirm and no fee: CAN-SPAM bars demanding any of them. The signed token is
  the authorization and the core verifies it.
- **Neither page is ever cached.** Both carry one person's state, so
  `NotificationPages::forbidCaching()` defines `DONOTCACHEPAGE` (which WP Super
  Cache, W3 Total Cache, LiteSpeed Cache and WP Rocket all read), calls
  `nocache_headers()` for the browser and any proxy, and sends
  `X-Robots-Tag: noindex, nofollow`. The shortcodes call it too, because a
  shortcode cannot know which page it is on until it runs.
- **The one-click POST answers the outcome as JSON and never a redirect**,
  which RFC 8058 forbids, so it is also the one POST in this plugin that is not
  a redirect-after-post.

The token rides as a path segment rather than a query parameter, so the URI in
the header is a path. The rewrite pattern is deliberately narrow
(`[A-Za-z0-9_.-]+`, the URL-safe base64 alphabet), so a path carrying anything
else is not a token and is not this page.

For a mail service that cannot send the `X-VidyaLMS-Feedback-Secret` header,
use `https://YOUR-SITE/wp-json/vidyalms-host/v1/feedback/email/FEEDBACK-KEY`.
Use a dedicated random key with 32 to 128 letters, numbers, underscores or dashes,
and store the same key in the host secret store referenced by the email channel.
Keep the callback URL private and redact its key in access logs. It is not a
WordPress account password or a Shondalai license key. Rotate both the stored
secret and the mail service's callback URL together.

For Amazon SES through SNS (Pro), set the exact **Amazon SNS topic** in the email
channel's settings. Add that topic's regional `sns.REGION.amazonaws.com` host
to **Settings → Network & security → Outbound hosts**. VidyaLMS verifies the
SNS signature against Amazon's certificate before confirming the subscription.
The standard SNS `text/plain` delivery format is supported. Mailgun, SendGrid
and Postmark can use the authenticated callback URL above.

**The feedback endpoint rides `vidyalms-host/v1` rather than the contract
namespace**, for the reason the upload endpoint does: the sender is a machine on
the far side of an ESP with no nonce, no cookie and no `Idempotency-Key`, and
`vidyalms/v1` is the shared contract whose routes this plugin must not
special-case. It takes the raw body, its content type and the
`X-VidyaLMS-Feedback-Secret` header, hands all three to the core route, and
emits the core's answer verbatim. There is no session and no capability check:
the shared secret in `provider_settings` is the authorization, and the core
answers a request without one without saying whether the channel exists.

A raw `message/feedback-report` body reaching the core at all is new. This mount
and both Joomla mounts now share `Core\Http\RequestBody`, which decodes a JSON
content type (or an absent one) exactly as before and carries any other content
type through untouched, so an ARF report is no longer answered 400 by the
adapter before the core sees it.

## The mail port, and what PHP mail() does to a structured header

`Port\WpMailer` honours four obligations, and three of them are legal rather
than aesthetic:

1. A message the core rendered is sent as authored, subject included.
2. A rendered message carrying an HTML part is sent as `multipart/alternative`
   with the plain part first, per RFC 2046 section 5.1.4. `wp_mail` sends one
   body, so the HTML is the body and `AltBody` is set on `phpmailer_init`, which
   is the assignment that produces that order; the reverse compiles and puts the
   parts the wrong way round.
3. Every entry of the header map is emitted verbatim. It travels in `wp_mail`'s
   headers array, which passes an unrecognised name straight to
   `addCustomHeader`. The `vidyalms_mail_headers` filter is asked first and the
   core's map is merged over the answer, so a site can add a `List-Id` or a
   stream tag and cannot remove `List-Unsubscribe`, `List-Unsubscribe-Post` or
   `Auto-Submitted`.
4. `envelopeSender` is written to PHPMailer's `Sender`, which is the SMTP
   `MAIL FROM` and not the `From` header; substituting the `From` address would
   attribute every bounce to the wrong stream.

The `phpmailer_init` listener is added for one send and removed in a `finally`
block, so a site sending its own mail between two of ours never inherits our
envelope sender.

**One limitation is PHPMailer's and is reported rather than hidden.** PHPMailer
runs every custom header value through `encodeHeader()`. With no control or
8-bit characters in it the only thing that triggers an encoding is the length,
and the length depends on the transport: `MAX_LINE_LENGTH` is 998 for SMTP and
sendmail, `MAIL_MAX_LINE_LENGTH` is 63 for PHP's own `mail()`, less sixteen
characters of Q-encoding overhead. So on a site sending through `mail()`, any
structured header value over 47 characters comes out as an RFC 2047
encoded-word, and an encoded-word is not permitted in a structured header value:
a receiver reading `List-Unsubscribe` finds no URI and one-click stops working
with nothing in any log.

The header is still emitted, because an inert header is not harmful and
silently dropping a legally required mechanism would be worse. What the port
does instead is write one line to the debug log naming the headers and the
remedy, which is to install an SMTP plugin. That is what Gmail's bulk sender
requirements effectively force anyway.

## Starting the sweeps

A sweep has no event behind it. Nothing happens when a drip window opens, when
a digest period closes or when a learner fails to log in, so something has to
notice, and the something is the host's own clock.

`Jobs\QueueRunner::startSweeps()` is that turn, on its own recurring event,
`vidyalms_run_sweeps`, hourly. Its own event and its own cadence rather than a
step inside the drain, because the two do different work: the drain empties a
bounded slice of the queue and has to run often, while a turn queues one row per
bin for every periodic handler and is idempotent over a period. Folded into the
drain it queued ninety-six rows on every five-minute tick and left the queue
permanently full of work that tick could not finish. The event is registered on
activation, healed on `init` beside the drain, and cleared on deactivate and
uninstall.

It knows no task type:
`Core\Application\Platform\EnqueuePeriodicTasks` walks the core's scheduled task
registry for handlers declaring `Registry\ScheduledTask\RunsPeriodically`, and
each of those answers its own bin count, period bucket and dedupe key. A sweep a
paid or third-party package registers is therefore started the day it registers,
with no change to this plugin, which is the same property that already lets the
drain run a job type this adapter has never heard of. The Joomla adapter calls
the same use case from its own routine.

The turn is idempotent inside a period, because the scheduler port replaces a
pending row carrying the same dedupe key. That matters more here than on Joomla:
WP-Cron fires on page load, so a busy site turns the clock several times a
minute.

`startSweeps()` answers how many rows the turn queued; `drain()`'s return value
is unchanged.

## The cron events are scheduled on activation

A fresh install needs no manual cron setup. `Setup\Activator` registers three
recurring WP-Cron events, and `Plugin::ensureQueueDrain()` heals all three on
`init` so a site that loses one to a cron plugin, a database restore or an
import gets it back on the next request rather than silently stopping.

| Event | Cadence | What it does |
|---|---|---|
| `vidyalms_run_jobs` | every 5 minutes | drains `{prefix}vidyalms_wp_jobs`, whatever queued a row |
| `vidyalms_run_sweeps` | hourly | one turn of the clock for every handler declaring `RunsPeriodically` |
| `vidyalms_run_expiry` | daily | the entitlement sweep, which declares no period of its own |

`vidyalms_run_expiry` is new and it closes a real gap. The entitlement sweep is
a whole-table pass with nothing to shard and a daily rather than a per-period
cadence, so it deliberately does not declare `RunsPeriodically` and
`EnqueuePeriodicTasks` passes it over. Nothing on this host started it: lapsed
entitlements never expired and their enrolments never suspended, which is
invisible until a learner keeps access to a course they stopped paying for. The
Joomla adapter runs the same use case from its own `vidyalms.expire_entitlements`
routine, so this is the WordPress half of one decision rather than a second
one. `Plugin`'s Settings and Dashboard figure now reports that event's own
cadence rather than the drain's.

All three are cleared on deactivate and on uninstall, and each is scheduled
only when `wp_next_scheduled()` says it is absent, so activating twice never
doubles a schedule and a site owner who rescheduled one keeps their cadence.

Where Action Scheduler is installed, punctual per-job execution goes through it
as before; these events are the floor rather than the only path.

## Credentials: verification, download and the PDF question

**The verification page is a PII disclosure surface, and it is treated as one.**
`Content\Templates::certificateContext()` calls the contract,
`GET /certificates/{code}/verify`, through `Content\CoreRoute` rather than
calling `VerifyCertificate` directly, and that is a security decision. The page
names a person against a course completion, so it is rate limited and marked
noindex, and `13-learning-flow-and-credentials.md` requires both to be **core
middleware** rather than a rule each adapter remembers: a control written once
per adapter covers only the routes that adapter happens to own, and this page
and the REST route are two transports over one disclosure.

The certificate route used to be forced **indexable** by `Templates::robots()`,
on the reasoning that the link is printed on the certificate. That reasoning is
wrong: printed links still resolve, they are simply not crawled into a
searchable index of who completed what. The route now joins the dashboard, the
player and the instructor page in the noindex group, and
`Templates::handleRequest()` sends `NoIndexMiddleware::HEADER` with the
middleware's own value, because a crawler that ignores the meta tag usually
honours the header.

The page renders only what the design permits: name, course, issuer, dates,
status and credits. Never an email, a user id, an enrolment id or the internal
certificate id. Every field is read defensively, so a build whose verification
shape has fewer fields renders fewer rows rather than a warning.

**Downloads are signed, expiring URLs and always an attachment.**
`Files\DownloadEndpoint` serves a private path only for a signature `WpStorage`
minted. `wp_check_filetype()` answers only for extensions the site allows as
uploads, and none of the credential formats are, so the endpoint names them
itself: `jsonld` as `application/ld+json`, `json` as `application/json`, `jwt`
as `application/vc+jwt`, `png` and `pdf` as themselves. Anything it cannot name
falls through to WordPress and then to `application/octet-stream`.

`html` is deliberately absent from that list. The free certificate artefact is
an HTML document assembled from a site-authored template, and naming it
`text/html` would run any script it carries on this origin. Every response
carries `Content-Disposition: attachment`, `X-Content-Type-Options: nosniff` and
`X-Robots-Tag: noindex, nofollow` besides.

**A credential can be bytes, and the core says so on the response.**
`ApiResponse` carries a decoded structure rather than a string, and one of the
free formats is a baked PNG, so a response holding bytes answers `isBinary()`
and hands them over through `binaryBytes()`.
`Rest\CoreBodyEmitter::binaryBody()` asks; it does not sniff. It used to: the
core wrote an inline literal `{"content": "<base64>", "encoding": "base64"}`
specified by a comment, and this emitter and the Joomla `RestController` each
carried their own heuristic for recognising it. Two emitters had to agree
forever on a rule written down nowhere, a third adapter would have invented a
third reading, and a drift there does not fail a test: it serves base64 text
where a wallet expected a PNG. The `WP_REST_Response` still carries the
envelope, so an internal `rest_do_request()` caller gets the structure while an
HTTP caller gets the file.

**WordPress gates no route on Accept, and that is the divergence worth naming.**
Joomla's `ApiApplication::route()` negotiates against the route's own media
type list before anything of ours is dispatched, so that mount has to be told
what the core can serve and now asks the credential format registry for it.
`register_rest_route()` has no equivalent: one route matches the whole
contract, the core owns every 406, and a format registered by a paid package is
reachable here the moment it registers with no change to this plugin.

**Kernel options this host supplies, and the two the credential surface
refuses without.** `Plugin::kernelOptions()` hands the core an options array of
host facts. None of these is ever taken from the request: issuance and bulk
reissue run from WP-Cron, a cron event has no request behind it, and a
credential minted there used to carry an unresolvable id for ever inside a
document that cannot be corrected once a wallet holds it.

| Option | Where it comes from | Absent |
|---|---|---|
| `verification_base_url` | the `verification_base_url` setting, else the filter `vidyalms_verification_base_url` | the verification URL is empty and the other two bases have nothing to default from |
| `credential_base_url` | `rest_url('vidyalms/v1/credentials')`, then the filter `vidyalms_credential_base_url` | `GET /credentials/{uuid}` answers **409** naming the option, rather than a document with a blank `id`, which is not an IRI |
| `status_list_base_url` | `<credential base>/status`, then the filter `vidyalms_status_list_base_url` | a `credentialStatus` entry cannot be minted and the same 409 applies |
| `site_name` | `get_bloginfo('name')` | the credential issuer name falls back to the issuer URL's host, then to a translated "not named yet"; never empty |
| `site_url` | `home_url()`, else the origin of the verification base | the issuer id falls back to `urn:vidyalms:issuer`, an IRI that is honestly not dereferenceable |
| `site_logo_url` | the site's custom logo where one is set | the `{site.logo_url}` token resolves to nothing and the seeded template draws no logo |

The last three default the `certificates.issuer` settings record, which an
administrator overrides through `PUT /vidyalms/v1/admin/settings`. That record
is the only thing on the Settings screen the API writes, and it is written
there because no WordPress settings form has a field for "who issues our
credentials": while nothing could write it, every credential this product
emitted named an anonymous issuer with an empty id and an empty name, both of
which are required members of the Open Badges 3.0 Profile.

**Every one of them is composed from a stored option, never from the request.**
`get_option('home')` and `get_bloginfo('name')` answer the same in a browser,
in WP-Cron and under WP-CLI, and `rest_url()` builds on the first of them.
Issuance is scheduled work: the certificate render, bulk reissue and the
backfill sweep all run without a request, and an id inside a signed document
can never be corrected afterwards because the only party who could is the
wallet holding it. The Joomla adapter reaches the same place by a different
road, because `Uri::root()` there **is** composed from the request and answers
the path of the CLI entry point when there is none.

**One data step runs outside the migrations.** `Activator::reconcileSeededData()`
is called from activation and, ahead of the version gate, from the
`admin_init` upgrade check, and it records its own marker option so the work
behind it runs once. It exists because a migration is keyed on the schema
version and only runs when the shape changes, while this has to reach a site
whose shape is already current and whose data is not, which is also why a
schema drift check cannot see it. Its one job today: schema 1.7.0 added
`certificate_templates.template_key` and did not fill it, so on every upgraded
site the shipped default carried NULL, a lookup by `vidyalms.default` missed
where a fresh install found it, and the two builds disagreed about which row is
the shipped template. The step claims exactly one row, the oldest unkeyed
default, and only when nothing already holds the key, because `template_key` is
unique and because a template an administrator created and made the default
must never be renamed under them.

**The certificate backfill needs no cron event of its own.**
`vidyalms.certificate.backfill` is a periodic handler in the core registry, so
the hourly `vidyalms_run_sweeps` event starts it like every other one. It
matters more than most: completion is terminal and `CourseCompleted` cannot
re-fire, so a completed enrolment whose issuance failed is a gap nothing else
in the product will ever look for. `build/smoke.php` asserts this handler is
among the ones one turn of the clock starts, rather than trusting that
registration implies provisioning.

**The free plugin renders certificates as HTML and bundles no PDF engine.**
Since 1.0.1 the Dompdf runtime is not in the plugin: the WordPress.org review
asked for it to go, and PDF rendering is a VidyaLMS Pro feature on both hosts.
The core registers its `html` and `elements` renderers unconditionally and its
`pdf` renderer only when `Ports` carries a `PdfPort`. `Plugin::portBundle()`
asks the `vidyalms_pdf_port` filter for one (`Plugin::FILTER_PDF_PORT`), once,
while it builds the bundle and before the kernel exists, which is the only
moment a port can arrive because `Ports` is readonly. The free plugin answers
null; Pro answers with its own renderer. An answer that is not a `PdfPort` is
logged and ignored, and a listener that throws is logged and costs only PDF
output. A `PdfPort` seated on `vidyalms_ports_ready` still replaces whatever
the filter answered.

Without a renderer the certificate artefact is an HTML document, stored under
`certificates/{id}.html` with the extension taken from the artefact's own media
type, downloaded through the signed endpoint as an attachment, and printed from
the browser. The verification page and the machine readable credential do not
depend on the renderer. A template whose renderer is `pdf` on a site without
Pro renders the core's "renderer missing" notice in place of the certificate,
so switch such templates to `html` or `elements` when Pro is removed.

`WpStorage::readPublic()`, the bounded public read a PDF renderer uses for
image elements, stays in the free plugin (`Files\BoundedPublicFile`) because
Pro's renderer runs against this plugin's storage port.

## The mount discovery key

`Admin\AdminApps::workbenchConfig()` and `Content\InstructorPage::mountConfig()`
both carry a `routes` key: every contract path template the running kernel
actually serves, once each and sorted, from `ApiKernel::servedTemplates()`.

It exists because the bundle and this plugin ship separately and a paid package
adds its routes from a `vidyalms_kernel_ready` listener, so which of the
contract's paths exist on an install is decided at boot and nowhere else.
Without the key the bundle had to guess, and it guessed wrong in the one
direction that matters: the quiz export control was on the contract, in the
generated SDK and in the shipped workbench, and answered 404 on every site
without the package that serves it. `packages/ui`'s `hasRoute()` reads the key,
and a route that is not listed is not offered.

It is a **discovery** key and never a permission key. Who may export is still
the core's answer to the request, which the app renders as a permission state;
this only says whether there is anything there to ask.

## The CPT is a shell

`vidyalms_course` exists so a course has a permalink, a canonical URL and whatever an SEO plugin
does with a public post type. It holds no LMS data. Courses, lessons, attempts, progress,
certificates and enrolments live in the `vidyalms_` tables and are written only by core use cases.
Storing course data in post meta would put a second source of truth next to the core, and is a bug.

## Importing

VidyaLMS > Import (`admin.php?page=vidyalms-import`) is the migration screen. It offers exactly the
importers the kernel registered, described by `Admin\ImportSources`, which asks each provider through
`supports()` whether it takes an upload, a `cms-db:` source or both: today `json-course` (`.json`),
`moodle-backup` (`.mbz`) and `community-quiz` (`cms-db:`, with an optional selector).

Beside the source controls it draws the options each importer **declares** through the core's
`ConfigurableImporterInterface`, one fieldset per importer, one control per declaration. This screen
holds no table of option names and never grows one: a QTI profile selector or a Moodle XML dialect
selector appears here the day the package registering that importer declares it. Every fieldset but
the chosen importer's is hidden **and disabled**, because hiding alone would still post one
importer's options with another importer's run, and with scripting off the first importer is the
selected one and its fieldset is the enabled one, so the screen still works. What comes back is read
through `ImportOption::read()` in the core rather than here, so this form and the Joomla one cannot
mean two different things: a ticked box reaches `import()` as a boolean and not as the string `"1"`,
which every importer's `( $options['flag'] ?? false ) === true` would have read as false.

Bytes never travel through the REST layer. `Admin\ImportPage` validates the upload (transport error, size
against `DEFAULT_MAX_UPLOAD_MB` filtered by `vidyalms_import_max_upload_mb` and capped by PHP's own
`upload_max_filesize` and `post_max_size`, extension against the allowlist the chosen importer narrowed),
writes it through the storage port under `imports/<user id>/`, and passes the private path as the source.

Preview runs inline and writes nothing; Run queues the job and answers immediately with a pending row.
The work happens in `Jobs\QueueRunner`, which drains `vidyalms.import.run` to `RunQueuedImport` on the
plugin's own cron hook. Drain it by hand with `QueueRunner::drain()`.

`community-quiz` reads Community Quiz tables in the host database through `Query::fromHostTable()`, so it
resolves them with the WordPress prefix (`wp_cq_courses`). Community Quiz is a Joomla component, so on a
normal WordPress site those tables do not exist and the importer fails cleanly, naming the missing table,
rather than importing half a course. It is registered here because the registry is the core's, not the
adapter's, and because a site that does hold those tables can use it.

Nothing is rolled back. A run that failed after eleven of twenty lessons has created eleven lessons, and
running the same source again is the recovery: `import_map` turns the second run into an update. That
recovery needs an identity that survives the fix, which is why a JSON document that will be corrected and
uploaded again must carry a `key` of its own: without one it is identified by a digest of its exact
content, so the corrected file would import as a second course. Every keyless run warns with the key to
add, and the screen says the same before you start.

Importer-specific options (`table_prefix`, `enrolments`, `publish` for Community Quiz; `max_bytes`,
`max_entries` for Moodle; `course_key` for the JSON importer, which supplies that identity without
editing the document) are not on the screen; the screen sends `dry_run` and the selector only. Set them
through `POST /wp-json/vidyalms/v1/import`.

The job list shows the notes that need attention above the log. It reads the level from the note rather
than from its text: a note is one line with control characters replaced, so no imported title can write a
line into the log or claim a level of its own.

## Privacy

`Exporter` and `Eraser` register with `wp_privacy_personal_data_exporters` and
`wp_privacy_personal_data_erasers`, so Tools > Export Personal Data and Tools > Erase Personal Data
cover the whole learning record. Both read and write through the core `DatabasePort`, never through
`$wpdb`. The export paginates over a fixed, ordered group list, so a large activity log cannot time
out a request. Erasure deletes the rows that describe the subject and anonymises the rows that
belong to somebody else (a course they authored, a grade they awarded), which is what keeps every
other learner's record and every aggregate intact. Both classes carry the full list in their
docblocks.

## Commerce

WooCommerce owns checkout, payments, orders, taxes, refunds, subscriptions and invoices.
VidyaLMS only synchronizes course access using `CoreKernel::syncShopAccess` with shop
`woocommerce` and object type `order` or `subscription`. No LMS payment/refund policy is run.

Setup:

1. Mark the course **Paid** in VidyaLMS. Free courses deliberately cannot be selected in the
   WooCommerce mapping fields; their self-enrolment rule would otherwise bypass checkout.
2. In WooCommerce product **General**, choose **Grants access to course**. Each variation also
   has a selector: inherit the parent, select another paid course, or explicitly select no course.
3. Configure the LMS `commerce.background_actor_user_id` setting to a real WordPress account
   permitted to enrol learners on every mapped course (typically the designated LMS manager).
   The integration does not choose the first administrator or match customer email addresses.
4. Enable WooCommerce account creation and configure its My Account page. Mapped carts require
   an account in both classic checkout and Checkout Blocks. Imported guest orders are held for
   account assignment and automatically retried. The learner's **My learning** page links to
   **Shop orders and subscriptions** in WooCommerce; no financial screens live in the LMS.
5. Keep WP-Cron running reliably. Failed access syncs retry after five minutes. An hourly sweep
   reconciles orders, subscriptions and tracked access sources in batches of 50. Trashed and
   deleted shop objects revoke their grants even when products or order items are already gone;
   restoring an eligible shop object reactivates access. Both WooCommerce and legacy WordPress
   deletion hooks enqueue a fresh read after deletion.

Shop lifecycle callbacks only enqueue work, so core transactions never run inside a shop's
payment, save or subscription transaction. Once initialized, WooCommerce's Action Scheduler
queues an async worker; WP-Cron is the fallback. New events remain queued even while another
worker is running. A worker re-reads committed shop state before changing access.

Access follows the shop's current state, re-read on every delivery. `WC_Order::is_paid()` is
honoured for processing, completed and custom paid statuses. An order item snapshots its course
and subscription ownership when created. Later catalogue edits and product deletion cannot
rewrite past purchases; changing an order/subscription item's product or variation refreshes its
mapping. A mixed cart gives its one-time lines order access and its subscription lines subscription
access. Subscription ownership never becomes an additional lifetime order grant.

A fully refunded quantity or line value removes that line's access. Partial line refunds and
fee-only refunds retain it, and another retained line for the same course still grants access.
Refund deletion, resumed payments and resumed subscriptions reactivate access through the core,
which preserves learner progress and unrelated manual/purchase grants. A refund of an older
subscription term does not revoke a newer paid term. Current-term refunds apply to the matching
subscription lines; WooCommerce remains responsible for cancelling future billing.

Active subscriptions expire at the next payment or end boundary, whichever comes first.
`pending-cancel` retains access through its prepaid `end` date; cancelled, expired and on-hold
subscriptions suspend access. Switches, item changes, date changes, renewal successes/failures and
regular reconciliation refresh the complete desired course set. Orders record private failure
notes once per distinct error, with details in the WooCommerce `vidyalms-access` log. Correct the
customer assignment, account permissions or mapping and the next retry repairs access.

All order/subscription metadata uses WooCommerce CRUD and queries use `wc_get_orders`; HPOS
compatibility is declared at plugin load. No order data is read from `wp_posts`/`wp_postmeta`.
Each sync holds a per-object MySQL advisory lock across the fresh shop read and access write.
A concurrent worker retries instead of applying an older snapshot. The bounded tracked-source
sweep reads the core `shop_access_links` ledger to find objects absent from WooCommerce queries;
all entitlement changes still go through `syncShopAccess`.

Contract references: [Woo order source](https://github.com/woocommerce/woocommerce/blob/trunk/plugins/woocommerce/includes/class-wc-order.php),
[Subscriptions action reference](https://woocommerce.com/document/subscriptions/develop/action-reference/),
[Subscriptions source](https://github.com/Automattic/woocommerce-subscriptions-core/blob/trunk/includes/class-wc-subscription.php),
[Action Scheduler API](https://actionscheduler.org/api/),
[HPOS extension recipe book](https://developer.woocommerce.com/docs/features/orders/high-performance-order-storage/recipe-book/).

## Installing on a test site

```
php build/build.php --install-to=<wordpress root>/wp-content/plugins
wp plugin activate vidyalms
```

`--install-to` copies the staged plugin straight into the plugins directory, which is faster than
uploading a zip on every change. Activation creates the tables through `dbDelta` and the roles and
capabilities.

### Schema upgrades

`Setup\Activator::SCHEMA_VERSION` is what decides whether a site has an upgrade to run.
`tooling/schema/version.php` holds the same number for the whole repository and the build fails when
the two disagree, because a constant left behind means a site upgrading to the new schema runs
neither `dbDelta` nor the migrations for it, and nothing says so.

`dbDelta` creates a missing table and adds a missing column, and that is the whole of its
vocabulary. Everything a version has to say about existing rows lives in
`vidyalms/schema/migrations/<version>.php`, a list of statements with a `{prefix}` placeholder, and
`Setup\Migrations` runs them straight after `dbDelta` in version order, skipping the versions the
site has already recorded. That folder is the WordPress counterpart of the Joomla component's
`sql/updates/mysql`, and the two halves of one version have to agree row for row.

The order is load-bearing, and so is what happens when it breaks: a migration writes into columns
`dbDelta` has just added, and the schema version is recorded last and only when every migration for
it ran cleanly. A failed migration therefore leaves the recorded version behind, so the next admin
request runs the same file again rather than declaring the site upgraded with its pins never written.
Every statement is written to be repeatable for exactly that reason.

An updated plugin is never reactivated, so the upgrade runs itself: `Plugin::boot()` hooks
`upgradeSchemaIfNeeded()` onto `admin_init`, in wp-admin only, because a front end request must never
find itself running DDL. From a terminal:

```
php build/upgrade.php [--wp=<wordpress root>] [--dry-run]
```

It checks the hook is registered and then calls the method the hook calls, which is worth more than
firing `admin_init` on a request that is not an admin request: the thing to prove is that the
callback wp-admin fires is the callback that ran.

Activating without wp-cli is a five line script, which is what CI does:

```php
require '<wordpress root>/wp-load.php';
require_once ABSPATH . 'wp-admin/includes/plugin.php';
$result = activate_plugin('vidyalms/vidyalms.php');
echo is_wp_error($result) ? $result->get_error_message() : "activated\n";
```

The plugin needs pretty permalinks: the catalogue, My learning and certificate verification are
rewrite rules, and WordPress registers none while Permalinks are set to Plain. The admin screens say
so with a notice and link to the setting. Both pretty shapes work, including the `index.php/`
PATHINFO structure WordPress falls back to where the server cannot rewrite.

## Running the smoke test

```
php build/smoke.php [--wp=<wordpress root>] [--actor=<user id>]
php build/smoke.php --cleanup
```

`build/smoke.php` bootstraps WordPress from the command line through `wp-load.php`, resolves the
kernel and drives the whole access spine against the real MySQL through the real ports. It is the
counterpart of `packages/adapter-joomla/build/smoke.php` and asserts the same things, because a
behaviour that holds there and not here is an adapter bug by definition.

Seventy-four assertions in fifteen sections: the kernel is a singleton and the schema is present; a
course, a module and two lessons are created and published and the permalink shell appears from the
core's own `CoursePublished` event, with nothing in the harness firing an adapter action, and
renaming the course renames the shell the same way; an
entitlement produces an enrolment; the same progress heartbeat replayed three times leaves one
`lesson_progress` row holding the accumulated seconds; completing both lessons completes the
enrolment at 100 percent, issues exactly one certificate, writes exactly one `course.completed`
activity row and refuses a replay; the certificate code verifies and an unknown code answers
`not_found` without throwing; a private file round-trips through `putPrivate`, `signedUrl`,
`verifySignature`, `readPrivate` and `delete` while a tampered signature and an expired link are
refused; a queued job is claimed, run and not claimed twice; `manage_options` reaches every
operational capability but not `vidyalms.admin`, while a subscriber and a guest are refused; the
`vidyalms_instructor` role reaches the workbench of the one course it is assigned to and is refused
both the reading and the writing of another, and `vidyalms_user_can_course` is proved to be asked and
able to narrow that answer further; `WpDatabase` satisfies the shared database port contract on real
MySQL; and the site's table list is unchanged.

Five later sections cover the learning-flow surfaces:

- **11f** assembles a rendered message through `WpMailer` and asserts the wire format rather than the
  port's own report of itself: both `List-Unsubscribe` header names intact, `Auto-Submitted` and
  `Precedence`, the `Feedback-ID`, `multipart/alternative` with the plain part before the HTML part,
  and PHPMailer's `Sender` carrying the envelope address. Nothing leaves the site: the capture runs
  on `phpmailer_init`, calls `preSend()` (which assembles and does not deliver) and then clears the
  recipients, so PHPMailer refuses the send on every machine rather than depending on this one having
  no transport.
- **11g** asserts that the two rewrite rules are stored rather than only registered, which is the
  failure a page fetch on a warm site would hide; that a GET of the landing page writes no preference
  and no consent row; and that a raw `message/feedback-report` body reaches the router rather than
  being answered 400 as bad JSON.
- **11h** asserts the mount discovery key on both workbench surfaces, including that a route the Pro
  plugin contributed is declared and that the front-end page declares the identical list.
- **11i** drives one turn of the clock end to end: probe handlers registered under the four task
  types this wave introduces, the turn run twice inside one period queuing no second row, and the
  drain running every queued row through the registry.
- **11j** gates a lesson on a future date over the contract and asserts the learner's own curriculum
  read comes back blocked with the instant, then creates and removes a cohort.

A check whose core route is not registered on the build under test prints `[PEND]` with the route
named, is counted separately from failures, and is reported in the summary. That is not a skip: a
check that can run and does not hold is still a `FAIL`, and each pending line becomes an ordinary
assertion the moment the core ships the route.

Three of those assertions are about the schema rather than the spine. `AssessmentFoundationContract`
(`tooling/contract`, shared with the Joomla adapter) asserts that the four tables schema 1.1.0 adds
answer a query, that every column 1.1.0 and 1.3.0 add is addressable in a predicate (counted per
version, because a site that stalled between them is a different problem from one whose 1.1.0 never
ran), that every
scoring policy key the migration wrote resolves in the free build's own registry, and that **every
attempt already on the site still reads**: through the attempt repository, through
`AttemptManifest::forAttempt()`, through `answersFor()` and `pendingCountFor()`. An attempt started
before 1.1.0 has no `attempt_questions` rows and reads through the pre-manifest fallback, a path no
fresh install can exercise because an attempt written today gets a manifest. The other two assert
that the recorded schema version matches the shipped one, and that the five-minute WP-Cron event and
its schedule are both registered, which is what the Settings and Dashboard screens quote the sweep
cadence from.

Whether the schema on a site is the schema a fresh install would create is a separate question, and
`tooling/schema/verify.php` answers it:

```
php tooling/schema/verify.php --wp=<wordpress root>
```

It creates a database of its own, runs this plugin's own compiled `schema/schema.php` into it,
compares both sides out of `INFORMATION_SCHEMA` and drops the database. Both sides come from the same
source of truth, so there is no second copy of the type mapping to drift. Run it after an upgrade: a
`dbDelta` that did not reach a column is invisible until the first write to it.

Adding `--pro` asks the same question of the Pro schema, against the Pro plugin's own compiled
statements. It is a separate run because the two are installed by different plugins and upgraded on
different days, and the comparison walks its own reference, so neither run sees the other edition's
tables. This plugin never installs a Pro table and the Pro plugin never installs a free one.

That port-contract section is `tooling/contract`, the same assertions the core runs against its
SQLite harness and the Joomla adapter runs against `JoomlaDatabase`: aggregates, conditional counts,
rates that answer null on an empty domain, `nullsLast` ordering, one level of OR, and `count()` of a
grouped query. Run it on its own with

```
php build/port-contract.php [--wp=<wordpress root>]
```

It writes inside a transaction it deliberately rolls back and then checks the rollback happened,
which matters most here: the tables have to be InnoDB, and on MyISAM the transaction statements are
accepted and do nothing.

Section 11l proves that availability gates a **write**, which is the half an outline cannot show.
It creates a third course of its own with a module, a reading lesson and a quiz, enrols the
throwaway learner, puts a date restriction three weeks out on the quiz and posts
`/quizzes/{id}/attempts` as that learner. The refusal has to be a 409 naming both the reason key and
the instant, and no attempt row may be written; clearing the rule is then the whole of unlocking it
and the next post starts an attempt. It runs on a course of its own because the spine's enrolment is
completed by the time the section is reached and `StartAttempt` requires an active one, and it
removes that course as soon as it is finished with it.

Section 11m is the credential surface around the certificate the run already issued: the frozen
`template_snapshot` and `context_snapshot`, a template with a page and four elements, a preview that
writes nothing, the credential document in each free format, a reissue that supersedes the old row
and leaves its code resolving, and a revoke with a reason. Every assertion in it is guarded by the
route it needs, so a build that has not registered the template aggregate or the credential routes
reports each one **pending** and names the route, and each becomes an ordinary assertion the moment
the core ships it.

The job-queue section asserts that a finished job is not claimed again **by row**, not by asking
whether the queue is empty. WP-Cron fires on page load, so a site that served any request during the
run can have a sweep row of its own waiting, and a drain that claims it is the queue working rather
than the finished row being taken twice. Asserting an empty queue made the check pass or fail on
whether anybody had visited the site.

That last section is the `SchemaSeal` the run takes at startup, reported out loud rather than only on
breach ("the table list is unchanged since the run started, N tables, 0 added, 0 dropped"), because a
detector that is silent either way cannot be told apart from one that was never wired in. The harness
seeds and removes rows; it creates no table and drops none. See `tooling/fixtures/README.md`.

Course cleanup is one function, `removeSmokeCourse()`, shared by the gated-quiz section and by
`--cleanup`. Two lists of tables would drift, and a table on one list and not the other is a leak
nobody notices until a later run trips over the row.

Every assertion prints PASS or FAIL with its evidence, and the script exits non-zero on any failure.
`--cleanup` removes everything a run seeded, including the throwaway users and role, and leaves the
plugin installed and active.

The storage section deliberately uses a file name holding a space and a percent sign. A plain name
passes whether the endpoint decodes the query path once, twice or not at all; an awkward one does
not, and a wrong answer there is a 403 on every certificate link.

## Static analysis

```
composer install --no-interaction
composer analyse
```

PHPStan runs at level 5 over `vidyalms/src` and is clean, the same bar and the same shape as the
Joomla adapter. The adapter's `composer.json` is for analysis only; the plugin has no Composer
dependencies and bundles no PDF engine. The generated `vidyalms/src/I18n` string files are excluded.

Nothing outside `vidyalms/src` is analysed. WordPress and WooCommerce arrive as stub packages,
`vidyalms/vidyalms.php` is scanned for the three global accessors it declares, and `vidyalms/core`
is the packager's copy of `packages/core/src`, which is analysed once, in `packages/core`, at level
8. `build/phpstan-bootstrap.php` defines the WordPress constants that no stub file declares because
WordPress itself defines them inside a function (`MINUTE_IN_SECONDS`, `MB_IN_BYTES`, `ARRAY_A`,
`WP_CONTENT_DIR` and their neighbours); every value there is the value WordPress sets.

Both `ignoreErrors` entries name a stub or a boot artefact, not a defect, and each says which
declaration is looser or stricter than the runtime object.

## Distribution constraints

wordpress.org's guidelines bind this plugin and are not negotiable:

* Nothing is locked, limited or waiting for a key (guideline 5). The free plugin is complete.
* No external HTTP request of any kind, no telemetry (guideline 7). Pro is a second plugin,
  distributed and updated from shondalai.com, never installed by this one (guideline 8).
* No remote asset. Every script, style and font is served from the plugin.
* All output escaped, all input sanitized, a nonce and a capability check on every write.
* Every user-facing string goes through the WordPress translation functions with the `vidyalms`
  text domain.

The plugin is **GPL v3 or later**, not GPLv2 or later. That is forced, not chosen: the core it
bundles is `GPL-3.0-or-later`, and GPLv3 code cannot be redistributed under a GPLv2-or-later
declaration. wordpress.org accepts GPLv3, so this is compatible with listing; `readme.txt`, the
plugin header, every file header and the shipped `LICENSE` all say the same thing.

## Limitations

Honest current state, verified against a real site rather than assumed.

* Blocks are registered server-side with a `render_callback` only. They render correctly wherever
  they are inserted, but they do not appear in the block inserter: that needs an editor script,
  which needs a JavaScript build step, and it belongs with the React work.
* `vidyalms_signed_url_ttl` and `vidyalms_catalogue_show_locked` are created on activation and
  deleted on uninstall, but nothing reads them yet. Their consumers are the certificate renderer and
  the locked-course catalogue treatment, both of which are later phases. They are documented options
  with no effect today.
* The catalogue takes a category id as a query var and as a block or shortcode attribute, but the
  public UI offers no category picker. The `vidyalms_course_category` taxonomy now exists and the
  admin course form uses its terms, so the data is there; the front end select is not.
* The site's `catalogue_per_page` deliberately does not apply to `GET /courses`. The REST contract
  keeps the core's default so the same request answers identically on WordPress and Joomla. Only the
  server rendered catalogue, the block and the shortcode follow the setting.
* A course slug containing a literal percent sign is decoded once by WordPress's rewrite layer and
  again by the core's `Route::match`, so such a slug resolves differently here than on Joomla. The
  first decode is in the host and cannot be undone from the adapter. It affects slugs and
  certificate codes holding percent signs, and nothing else.
* The queue runner is driven by WP-Cron unless Action Scheduler is installed, so on a quiet site a
  job runs when the next visitor arrives, not on the minute. That is WP-Cron, not the runner.
* The product course selector lists at most 500 paid courses. A saved paid course beyond that
  stays selected and is shown by id.
* Multisite gives each site its own tables and its own courses. There is no network-wide view.
* Personal data erasure runs in a single page. It is bounded by one learner's own records, which is
  fine at any realistic size, but it is not chunked the way the exporter is.
* One-click unsubscribe needs SMTP. PHPMailer Q-encodes any custom header value over 47 characters
  when the site sends through PHP's own `mail()`, and an encoded-word is not a URI, so
  `List-Unsubscribe` arrives unusable. The header is still sent and the port writes one line to the
  debug log naming the remedy, which is to install an SMTP plugin. See "The mail port".
* The unsubscribe page and the preference centre need pretty permalinks, like every other VidyaLMS
  route: on "Plain" they have no path and only the query-var form answers. The admin notice that
  already says so covers them.
